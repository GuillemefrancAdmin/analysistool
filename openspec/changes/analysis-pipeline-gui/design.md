## Context

The repository already runs one concrete workflow: a 9-stage source/business-process analysis over `source code/` and `Processus affaires/`, using `skills/*/SKILL.md` (prompt/role text per stage), `templates/source-code-analysis-schema.json` (final-stage output schema), and live `.analysis-state/` data — a real queue, state files, and dozens of existing checkpoints from actual runs. `scripts/generate_analysis_queue.ps1` scans the source roots and writes `.analysis-state/queue/manifest.json` plus one `states/<file>.state.json` per file; `scripts/run_analysis_pipeline.ps1` (and its `_parallel` wrapper) reads the queue, runs each queued file through the 9 stages against a local Ollama endpoint, validates the final stage's output, writes results under `.analysis-state/outputs/`, and updates state + `.analysis-state/checkpoints/`. Stage order and count are implicit (hardcoded in the script, mirrored in `documentation/diagram.md`).

The operator's need is broader than this one workflow: a local desktop tool for running *any* long-lived, multi-stage LLM workflow, where different stages (or different workflows entirely) can use different local LLM "skills"/models, executed unattended against a file set for hours or days. The legacy 9-stage analysis is the first real workflow, not the whole product — the app's data model and UI need to treat "workflow" as a first-class, pluggable concept from the start, with that legacy process migrated in as the bundled default/sample workflow (`legacy-source-analysis`), preserving its existing on-disk history.

The application is named **Analysis Pipeline Studio** (solution/executable: `AnalysisPipelineStudio`, per `tasks.md` task 1.1).

## Goals / Non-Goals

**Goals:**
- Single C# desktop application: define, run, monitor, and fully control any number of workflows (start/pause/resume/stop/reset), replacing `scripts/*.ps1`.
- Workflows are first-class and operator-definable: each has its own ordered stage list, prompts, output schema, and source root(s), stored under its own `workflows/<workflow-id>/` directory, with isolated `.analysis-state/<workflow-id>/` run state, and optionally its own LLM/model defaults distinct from other workflows.
- The legacy 9-stage source/business-process analysis ships as the built-in default workflow (`legacy-source-analysis`), migrated from the current `skills/`, `templates/source-code-analysis-schema.json`, and `.analysis-state/` content with no loss of existing history (checkpoints, states, outputs already on disk).
- Native, in-process implementation of queue discovery, one-file-at-a-time / multi-worker execution, checkpointing, resume, and stall detection/retry — functional parity with today's `.ps1` behavior, generalized to any workflow.
- Support multiple workflows existing side by side and, resources permitting, running concurrently for long unattended stretches, each able to target a different local LLM endpoint/model ("different LLM skill" per workflow or per stage) without the operator having to hand-edit anything.
- A GUI editor for the selected workflow's ordered list of stages, each stage's prompt/role definition, per-stage model parameters, and its output schema — so a workflow can be shaped without hand-editing files.
- A workflow management surface: create, clone, rename, delete, and import/export workflow definitions, and switch which workflow the rest of the app is scoped to.
- Continue to use flat, git-diffable on-disk JSON/Markdown as the source of truth (now under `workflows/` and per-workflow `.analysis-state/<workflow-id>/`), so in-flight state isn't lost and the change is additive to what already exists.
- An output browser for the selected workflow's generated artifacts.
- A mandatory first-run LLM setup step and a persistent in-app chatbot, backed by that local LLM, with full control over workflow management, workflow configuration, and run state — the app should feel LLM-guided from the first launch, not just LLM-executing. The chatbot acts directly on low-risk changes and only stops to ask the operator when an action is high-risk, and can draft an entirely new workflow from a description, not just edit the bundled one.
- A stage can contain multiple sequential steps, each its own prompt/model unit; a visual canvas shows a workflow's stages and steps as connected nodes and is the primary place to add/remove/reorder them, with per-node detail editing still available through the structured/raw-Markdown editor.
- Explicit save/load for the workflow currently being edited: changes are held as an in-memory draft with an unsaved-changes indicator until the operator saves or discards them.
- The output schema is edited as a structured node tree, each node mappable to the stage/step that produces it; an unmapped node can scaffold a new step directly, and the engine merges per-step outputs into one structured JSON result validated against that schema.
- Workflow runs can be scheduled (start date/time, recurrence, max run time, retry count/interval) by registering native Windows Scheduled Tasks, so triggering and enforcement of those limits is handled by the OS rather than a custom in-app scheduler.

**Non-Goals:**
- No changes to the contents of `source code/`, `Processus affaires/`, or any other workflow's source root(s) — those stay analysis inputs only.
- No cross-platform support — Windows desktop only, matching where the pipeline already runs.
- No multi-user/server mode, auth, or remote access — single local operator tool, same trust model as running the scripts today.
- No change to the underlying inference approach (still local Ollama-compatible HTTP endpoints) — the app calls the same kind of API the scripts call today, it doesn't add a new model runtime; "different LLM skill per stage/workflow" means different model names/endpoints against that same kind of API, not a new provider integration.
- Chatbot-authored PowerShell scripts are not a second pipeline execution path — every workflow's stages are still run exclusively by the native C# engine. Scripts are ad hoc workflow automation the operator explicitly requests (bulk file/state operations, cleanup, queries), not a way to reintroduce PowerShell into stage execution.
- Not migrating `source code`/`Processus affaires` scanning logic beyond what `generate_analysis_queue.ps1` already does (same discovery rules, ported not redesigned, now parameterized by workflow rather than hardcoded).
- Not building a workflow marketplace or remote sharing service — import/export is local file in/out only.
- Not implementing branching or parallel step execution within a stage in v1 — steps run strictly in the order defined; the data model is forward-compatible (each step has an explicit id and order) but the engine does not schedule steps as a DAG yet.
- Not building a cross-machine or cloud scheduler — scheduling relies on the local Windows Task Scheduler on the machine the app is installed on, same single-operator/local-only trust model as the rest of the app.

## Decisions

**1. UI framework: WPF on .NET 8, MVVM (CommunityToolkit.Mvvm).**
WPF gives mature native-Windows data binding and layout for a dashboard-plus-forms app, and ships in-box with .NET 8 (no extra runtime story beyond the .NET desktop runtime). Alternatives considered: WinForms (weaker data binding for live-updating grids/trees, harder to keep an editor UI maintainable); Avalonia (cross-platform benefit not needed, adds an unfamiliar dependency); Blazor Hybrid/Electron-with-.NET-backend (reintroduces a local web server / browser runtime, which is exactly the "no more scripts, one app" outcome the user rejected when they chose C# over a local web app).

**2. State storage stays as flat JSON/Markdown files under `workflows/` and `.analysis-state/` — no database.**
The existing schema (`templates/queue-manifest-template.json`, `state-file-template.json`, `checkpoint-template.json`) is already the contract other tooling (and `documentation/diagram.md`) describes, and continues to apply per workflow. Keeping flat files means no migration to a new storage engine and the files stay git-diffable/human-readable. The app reads/writes these directly and uses `FileSystemWatcher` (debounced) to refresh views when files change on disk. Alternative considered: embedded database (SQLite) for the dashboard's live view — rejected for v1 since queue/state volume is per-file JSON, not high-frequency, and a DB would need a JSON-import/export layer anyway to stay compatible with the existing on-disk contract.

**3. Workflow definitions live under `workflows/<workflow-id>/`, each with its own `manifest.json`; a stage is a group of one or more ordered steps.**
Stage order today is implicit (hardcoded in `run_analysis_pipeline.ps1`, mirrored by hand in `documentation/diagram.md`) and scoped to one pipeline. To let the GUI define, reorder, and run more than one workflow, each workflow gets its own directory: `workflow.json` (id, display name, description, source root(s), optional workflow-level model/temperature defaults), `manifest.json` (ordered stage list; each stage has id, display name, position, and an ordered `steps` list — each step with its own id, display name, position within the stage, its `skills/<stage-id>/<step-id>/SKILL.md` path, and per-step model/temperature/timeout overrides), `skills/<stage-id>/<step-id>/SKILL.md` per step, and `schema.json`. `documentation/diagram.md` becomes generated/derived from the built-in workflow's manifest rather than hand-maintained (or is left as historical documentation — see Open Questions). Alternative considered: keep one global manifest and namespace stage ids by workflow — rejected, it conflates unrelated workflows' stage lists and makes deleting or exporting one workflow harder than deleting/copying a directory. Alternative considered for steps: treat "step" and "stage" as the same flat concept (no nesting) — rejected per operator direction that a stage can contain multiple steps; nesting also gives a natural place to later add step-level branching without renaming the top-level stage concept.

**4. Step prompt content stays Markdown (`workflows/<workflow-id>/skills/<stage-id>/<step-id>/SKILL.md`), parsed by section, with a raw-edit fallback.**
Each `SKILL.md` already follows a consistent shape (Role/Mission/Inputs/Responsibilities/Workflow/Expected output/Quality rules). The editor parses those headings into form fields for structured editing, but always offers a raw Markdown view so content that doesn't fit the template isn't lost or blocked. This applies uniformly regardless of which workflow or stage a step belongs to; a stage with only one step (as every migrated legacy stage initially has) behaves exactly as a single-step "stage" did before steps existed. Alternative considered: convert step definitions to structured JSON — rejected because it would discard the current git-friendly, human-readable format for content that's fundamentally prose (agent instructions), and the user didn't ask for a format change, only a GUI to edit them.

**5. Execution engine ported in-process, generalized to run any workflow, and able to run multiple workflows concurrently.**
`run_analysis_pipeline.ps1`'s worker partitioning (`-WorkerIndex`/`-WorkerCount`), stall-guard/retry, and optional `ollama serve` auto-start (`-NoAutoStart`, `-CudaVisibleDevices`) are ported to in-process async workers, one worker pool per active workflow run, each pool bound to that workflow's configured endpoint(s) and coordinated over that workflow's own `.analysis-state/<workflow-id>/queue` + `.analysis-state/<workflow-id>/locks` files, so a worker's partitioning logic matches today's within a workflow while staying isolated across workflows. Two workflows can run at the same time as long as their configured endpoints/GPUs don't conflict; the app does not arbitrate GPU contention beyond what the operator configures (see Decision 11). Auto-starting/pinning `ollama serve` processes per GPU is ported but exposed as an explicit, off-by-default setting per endpoint, since getting GPU process management wrong is a bigger failure mode than requiring the operator to have Ollama already running.

**6. Run configuration: app-wide defaults in `.analysis-state/app-config.json`, overridable per workflow in `workflow.json`.**
Endpoint URL(s), model, worker count, timeouts, stall thresholds, and GPU assignment move from CLI parameters into an editable, persisted app-wide settings surface, bootstrapped from `run_analysis_pipeline.ps1`'s current defaults (e.g. `http://localhost:11434/v1`, `llama3.1:8b`, `Temperature 0.2`) so behavior doesn't silently change on adoption. Any workflow may override the endpoint/model/worker defaults in its own `workflow.json`; any stage may override further; and any individual step may override further still, in the workflow's `manifest.json` (Decision 3) — resolution order is step override → stage override → workflow override → app-wide default.

**7. First launch is gated behind a mandatory LLM setup wizard.**
On startup, if `.analysis-state/app-config.json` has no working LLM endpoint/model (or the configured one fails a connection test), the app opens a setup wizard first and keeps workflow management, the dashboard, stage editor, and output browser inaccessible until the operator configures and successfully tests a connection. This makes "configure the LLM" the actual first step of using the app, rather than an implicit assumption baked into script defaults (Decision 6). The wizard writes the same `app-config.json` fields Decision 6 already defines, so there's one settings surface, reachable again later from Settings to change the connection.

**8. In-app chatbot has full control of the app, gated by risk tier — not a blanket approve-every-change flow.**
A persistent chatbot panel (available from the dashboard, workflow management, the canvas, and the stage editor) is backed by the same configured Ollama-compatible endpoint. It can read and write everything the operator can reach through the UI: the workflow catalog (`workflows/**`), the selected workflow's `manifest.json`, its step `SKILL.md` files, its `schema.json`, its `layout.json`, `.analysis-state/app-config.json` settings, and run control (start/pause/resume/stop/reset) for any workflow. Low-risk, reversible actions — editing a step's prompt, reordering stages/steps, adding a stage or step, adjusting per-step/per-stage/per-workflow model/temperature/timeout, editing a schema and its node-to-step mapping, creating or cloning a workflow, starting/pausing/resuming a run — are applied directly, through the same save/validation path the structured editors use (Decision 4, and the schema-validation requirement in `stage-definition-editor`), and recorded in a chatbot action log the operator can review afterward; no blocking confirmation dialog for these. The chatbot must stop and get explicit operator confirmation before: removing a stage that has already-recorded completions in existing state files, deleting an entire workflow, resetting the entire queue for a workflow, stopping or resetting a currently active run, or changing the configured LLM connection away from one that is currently working. Regardless of risk tier, a write that fails validation (invalid schema, malformed manifest) is never applied — it's rejected and reported back to the operator the same as a failed manual save. Alternative considered: require approval on every proposed change — rejected per operator direction (the assistant should have full control, not act as a suggestion box); full write/run-control access with a validation floor, a narrow confirmation list for irreversible actions, and an audit log gives real autonomy without removing the safety net.

**9. Chatbot-authored PowerShell scripts are scoped to the selected workflow, visible, and risk-gated like any other chatbot action.**
When the operator asks for something better done as a script (bulk state cleanup, ad hoc filtering/reporting over a workflow's state, one-off file operations), the chatbot can draft a PowerShell script and run it as a child process, capturing stdout/stderr/exit code back into the chat and the chatbot action log (Decision 8). The script's content and result are always shown, whether or not the run required confirmation. Execution is scoped by default to the app's managed directories for the currently selected workflow (`workflows/<workflow-id>/`, `.analysis-state/<workflow-id>/`, `.analysis-state/app-config.json`, and an app-defined scratch directory) with no network access; a script becomes high-risk — and joins Decision 8's confirmation list — the moment it would touch any path outside that scope (including any workflow's source root(s), which stay off-limits per the existing output-browser restriction, or another workflow's directory), delete/overwrite files, or make a system/process-level change. Alternative considered: let the chatbot only suggest scripts for the operator to copy/run manually — rejected per operator direction that the assistant should have full control, not act as a suggestion box, consistent with Decision 8.

**10. On-disk migration: existing `skills/`, `templates/source-code-analysis-schema.json`, and `.analysis-state/` content moves into `workflows/legacy-source-analysis/` and `.analysis-state/legacy-source-analysis/`.**
This repository already has real run history (existing checkpoints, state files, and outputs under `.analysis-state/`), so this is a data migration, not a fresh seed. `skills/<id>/SKILL.md` files move to `workflows/legacy-source-analysis/skills/<id>/SKILL.md`; `templates/source-code-analysis-schema.json` moves to `workflows/legacy-source-analysis/schema.json`; a new `workflows/legacy-source-analysis/manifest.json` and `workflow.json` (source roots `source code/`, `Processus affaires/`) are generated from the current implicit stage order (`documentation/diagram.md`). The existing `.analysis-state/{queue,states,checkpoints,locks,outputs}` moves under `.analysis-state/legacy-source-analysis/`, preserving every existing file; `.analysis-state/app-config.json` stays at the top level. The move is implemented as a one-time, idempotent bootstrap step that runs before the app reads any workflow state, and is verified by comparing file counts/hashes before and after.

**11. Concurrent multi-workflow execution and per-workflow LLM assignment are explicit, not automatic load-balancing.**
Each workflow's run has its own worker pool bound to that workflow's configured endpoint(s) (Decision 5/6). The app does not automatically detect or prevent two concurrently-running workflows from pointing at the same endpoint and contending for it — if the operator wants two workflows to run in parallel without contention, they configure them with different endpoints/GPU assignments, the same way they'd configure separate workers today. The dashboard's workflow switcher shows all currently-running workflows (not just the selected one) so the operator can see everything running unattended at a glance. Alternative considered: have the app auto-schedule/queue workflow runs against a shared resource pool — rejected for v1 as unnecessary complexity; the operator already has to reason about GPU/endpoint capacity manually today, and auto-scheduling can be a later enhancement if needed.

**12. Deleting a workflow and authoring a brand-new one are both chatbot capabilities, gated the same way manual actions would be.**
The chatbot can draft a complete new workflow (stages, prompts, schema, suggested source root) from a natural-language description the same way workflow-management lets an operator create one manually; a freshly-drafted workflow that hasn't been activated yet is low-risk (it doesn't affect any other workflow and is trivially deletable). Deleting an existing workflow — chatbot-initiated or manual — is treated as high-risk (Decision 8's confirmation list) because it removes an entire `workflows/<workflow-id>/` definition and, if the operator confirms it, that workflow's `.analysis-state/<workflow-id>/` run history.

**13. Steps within a stage execute strictly sequentially in v1; the data shape is forward-compatible with future branching.**
Each stage's `steps` list (Decision 3) runs in order, one step at a time, the same way stages themselves execute today — a step's output is available to the steps after it, and the file's overall per-stage result is the combination of its steps' outputs. No parallel or conditional execution is implemented. Each step still carries an explicit `id` and `position`, and stage/step identifiers are stable, so a later change could add an optional `dependsOn`/edge concept for branching without renumbering or renaming existing steps. Alternative considered: build branching/parallel step execution now — explicitly deferred per operator direction ("sequential for now, future can be parallel"); it would require topological scheduling and per-step concurrency control in the engine that isn't justified until a workflow actually needs it.

**14. The workflow canvas is a structural editing surface over the same `manifest.json`; node layout lives in a separate `layout.json`.**
`workflows/<workflow-id>/layout.json` stores each stage's and step's canvas position (and any purely visual grouping) keyed by stage/step id. The canvas reads `manifest.json` to know what nodes and connections to draw and reads `layout.json` for where to draw them; adding, removing, or reordering a node on the canvas writes to `manifest.json` (same save/validation path as the structured editor), while dragging a node to a new position writes only to `layout.json`. Selecting a node opens that step's (or stage's) detail form (Decision 4). Alternative considered: store position data as extra fields inside `manifest.json` — rejected because it would make every cosmetic drag-and-drop change show up as a diff to the execution-relevant file, and would force the pipeline engine's manifest reader to ignore fields it doesn't care about.

**15. Output schema editing becomes a structured node-tree editor with an explicit node-to-step mapping, stored in `schema.json` via an `x-producedBy` extension.**
`schema.json` stays a JSON Schema document (Decision unchanged from the original schema-validation requirement), but each node may carry an `x-producedBy: "<stage-id>.<step-id>"` extension keyword recording which step's output populates it. The editor renders the schema as a tree the operator can browse and edit field-by-field (rather than only as raw JSON text, though the raw view remains available per Decision 4's precedent), lets the operator pick or change a node's producing step, and lets the operator scaffold a brand-new step directly from a selected unmapped node (pre-filling that step's expected output shape from the node's schema type). A node with no mapped producer is flagged as a non-blocking warning, both in the editor and before a run starts, since a workflow might still be under construction. Alternative considered: track the node-to-step mapping in a separate `schema-mapping.json` — rejected, since keeping the mapping and the schema in one file avoids the two drifting out of sync when a node is renamed or removed.

**16. Explicit save/load for in-progress workflow edits, decoupled from the chatbot's direct-write model.**
The canvas and stage editor operate on an in-memory draft of the selected workflow; the operator explicitly saves (writing the draft to `manifest.json`/`layout.json`/`schema.json`/step `SKILL.md` files) or discards it, with an unsaved-changes indicator shown while a draft differs from what's on disk. This is distinct from the chatbot's direct-write model (Decision 8): the chatbot's low-risk actions still write straight to disk, since the point of Decision 8 is that it doesn't need approval. If the chatbot modifies a workflow the operator currently has open with unsaved canvas/editor changes, the app surfaces a conflict warning rather than silently discarding either side's changes (see Risks). Alternative considered: auto-save every change immediately, same as the chatbot — rejected because free-form canvas editing (dragging nodes, wiring connections mid-thought) benefits from an explicit, reversible save point the way file-based tools normally work, which the operator asked for directly ("save and load the workflow he is working on").

**17. Scheduling is implemented as native Windows Scheduled Tasks the app creates and manages, not a custom in-app scheduler.**
The app uses the Windows Task Scheduler API (e.g. the `TaskScheduler` managed wrapper) to register one scheduled task per scheduled workflow run. The trigger's start date/time and recurrence map to a native Task Scheduler trigger; "max run time" maps directly to that trigger's `ExecutionTimeLimit`; "retry count/interval" maps directly to the task's `RestartCount`/`RestartInterval` settings — the app does not reimplement any of this itself, it only builds the task definition and lets Windows enforce it. The task's action launches the app executable with a headless/unattended command-line flag identifying which workflow to run. On a headless launch, the app first checks for an already-running instance (named mutex); if one exists, it hands off the run request to that instance over a local named pipe instead of starting a second process, and if none exists, it starts the requested workflow's run with no visible window and exits when the run completes, stops, or hits its time limit. The app manages the full lifecycle of tasks it created (list/edit/delete) from within its own scheduling UI so the operator never has to leave the app to use Task Scheduler directly, even though Task Scheduler is doing the actual triggering. Alternative considered: build an in-app scheduler that only fires while the app is open — rejected per operator direction; it would silently fail to run anything whenever the app isn't open, defeating the point of unattended long-running workflows, and would require reimplementing execution-time-limit and retry logic Windows already provides.

## Risks / Trade-offs

- **[Risk]** Porting stall-detection and worker-partitioning logic from PowerShell to C# introduces behavior drift (e.g. different stall timing, different file-claim races) → **Mitigation**: keep `scripts/*.ps1` in the repo and runnable during a transition period; validate the C# engine against the same queue fixture and compare resulting state/checkpoint files before treating the scripts as fully superseded.
- **[Risk]** Running the new app and a legacy `.ps1` invocation concurrently against the same `.analysis-state/legacy-source-analysis/` could double-claim a file or corrupt a state file → **Mitigation**: both paths already coordinate via that workflow's `locks/` directory; document that the app and scripts must not be run against the same queue at the same time during transition.
- **[Risk]** Structured (section-based) parsing of `SKILL.md` could mis-parse a stage file that drifts from the expected heading shape, silently dropping content on save → **Mitigation**: raw-Markdown fallback view (Decision 4) plus a diff/preview step before any write.
- **[Risk]** `FileSystemWatcher` over a workflow's `outputs/` (potentially many small files during a full-queue run) can flood the UI thread with change events, and watching many workflows at once multiplies this → **Mitigation**: debounce/batch watcher events per workflow before triggering view refreshes; only actively watch the selected workflow plus any others currently running.
- **[Trade-off]** Choosing WPF/.NET desktop over the earlier "local web app" option means no remote/browser access to the dashboard — acceptable since this is a single-operator local tool per the clarified requirements.
- **[Risk]** A mandatory setup gate could block the operator from ever reaching the dashboard if the local Ollama instance is genuinely unreachable at first launch (e.g. not installed yet) → **Mitigation**: the wizard's connection test gives an actionable error (what URL/model was tried, what failed) and the wizard can be re-run from Settings without reinstalling the app; it does not require the model to be pulled yet, only the endpoint to respond.
- **[Risk]** Giving the chatbot full write and run-control access increases the blast radius of a plausible-looking but wrong LLM action (bad stage prompt, wrong reorder, bad schema edit, stopping a run it shouldn't have, deleting the wrong workflow) → **Mitigation**: every chatbot write still goes through the same validation as a manual edit (Decision 4, schema check), the narrow list of high-risk actions in Decision 8 (including workflow deletion, Decision 12) always requires explicit confirmation before executing, and every chatbot-initiated change is recorded in an audit trail distinguishable from manual edits so the operator can spot and revert unwanted changes quickly via the underlying git-diffable files (Decision 2).
- **[Risk]** Chatbot-authored PowerShell execution (Decision 9) is the highest-blast-radius capability added — it can, in principle, act on the filesystem or processes beyond the app's own JSON/Markdown files → **Mitigation**: default execution scope is restricted to the selected workflow's managed directories with no network access, anything outside that scope or destructive is treated as high-risk and gated behind the same confirmation as Decision 8's other high-risk actions, and script content plus captured stdout/stderr/exit code are always shown and logged so a failed, partial, or unwanted script run is immediately visible rather than silent.
- **[Risk]** The one-time migration of existing `skills/`, `templates/`, and `.analysis-state/` content into `workflows/legacy-source-analysis/` and `.analysis-state/legacy-source-analysis/` (Decision 10) could lose or misplace real run history if done carelessly → **Mitigation**: migration is a scripted, idempotent, verified move (not a rewrite) with a before/after file count and checksum comparison, run once before the app reads any workflow state, and the original paths are only removed after verification succeeds.
- **[Risk]** Allowing multiple workflows to run concurrently without automatic resource arbitration (Decision 11) could let the operator accidentally point two workflows at the same GPU/endpoint and degrade both → **Mitigation**: the dashboard surfaces every currently-running workflow and its configured endpoint together, so a conflicting assignment is visible at a glance; this is treated as an operator configuration concern, not a bug, consistent with how GPU assignment already works today via script parameters.
- **[Risk]** A headless-launched scheduled run (Decision 17) could double-launch the app if single-instance detection is buggy, or could silently fail to hand off to an already-open instance → **Mitigation**: single-instance detection uses a named mutex checked before any workflow state is touched, and the named-pipe handoff is verified in the parity/validation pass (task list to be added) by triggering a scheduled task both while the app is closed and while it's already open, confirming exactly one run starts either way.
- **[Risk]** Registering/editing Windows Scheduled Tasks could fail silently or require permissions the operator doesn't have (e.g. task folder ACLs) → **Mitigation**: the scheduling UI surfaces the Task Scheduler API's own success/failure result for every create/edit/delete, and scheduling is scoped to the current user's task folder (no "run whether user is logged on or not" / elevated mode) so it doesn't require admin rights by default.
- **[Risk]** Splitting node layout into `layout.json` (Decision 14) and the node-to-step schema mapping into `x-producedBy` extensions on `schema.json` (Decision 15) adds two more files/fields that must stay consistent with `manifest.json` as stages/steps are added, renamed, or removed → **Mitigation**: stage/step ids are the join key across all three; deleting or renaming a stage/step through the canvas or editor updates `layout.json` and any `x-producedBy` references to it in the same save operation, and a dangling reference (an id in `layout.json` or `schema.json` with no matching manifest entry) is treated as a non-blocking warning, not silently ignored.
- **[Risk]** The explicit save/load draft model (Decision 16) could let the chatbot's direct writes and the operator's unsaved canvas edits diverge, with one silently overwriting the other → **Mitigation**: the app detects when the chatbot writes to a workflow the operator has open with unsaved changes and surfaces a conflict warning (showing what the chatbot changed) rather than auto-merging or discarding either side; the operator decides how to reconcile before saving their draft.

## Migration Plan

1. Design and implement the one-time repository migration (Decision 10): move `skills/<id>/SKILL.md` → `workflows/legacy-source-analysis/skills/<id>/<id>/SKILL.md` (each of the 9 existing stages becomes a stage with exactly one step, reusing the stage id as its sole step's id, per Decision 3 — no change in run behavior); move `templates/source-code-analysis-schema.json` → `workflows/legacy-source-analysis/schema.json`; generate `workflows/legacy-source-analysis/manifest.json` and `workflow.json` from the current 9-stage order (per `documentation/diagram.md`) and source roots (`source code/`, `Processus affaires/`); generate an initial `workflows/legacy-source-analysis/layout.json` with a simple left-to-right auto-layout of the 9 single-step stages; move `.analysis-state/{queue,states,checkpoints,locks,outputs}` → `.analysis-state/legacy-source-analysis/{...}`, preserving every existing file.
2. Add `.analysis-state/app-config.json` seeded from `run_analysis_pipeline.ps1`'s current default parameter values (app-wide; used only to pre-fill the setup wizard, not to skip it).
3. Verify the migration: compare file counts and checksums for the moved `.analysis-state/legacy-source-analysis/` content against the original `.analysis-state/` content before removing the old paths.
4. Ship the app able to read the migrated `workflows/legacy-source-analysis/` and `.analysis-state/legacy-source-analysis/` unmodified thereafter — no further schema migration needed for that workflow's data.
5. Run the C# engine side-by-side with the `.ps1` scripts (not concurrently on the same queue) against a copy of the migrated legacy workflow to confirm parity, then adopt the app as the normal way to run any workflow.
6. Mark `scripts/*.ps1` as superseded (comment header noting the app replaces them); actual deletion is left to a future change once the app has been used for real runs.

Rollback: since the migration is a move (not a destructive rewrite) and verified before old paths are removed, if the app misbehaves the operator can restore `skills/`, `templates/`, and `.analysis-state/` from the pre-migration layout (or from git history) and resume using the original `.ps1` scripts with no further data conversion needed.
