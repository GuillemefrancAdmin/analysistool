## Why

The legacy-source analysis pipeline (9 skill stages, queue/state/checkpoint tracking under `.analysis-state/`, and execution driven by `scripts/*.ps1` calling a local Ollama model) currently has no visual surface, and — just as importantly — nothing in the code or file layout treats "the 9-stage COBOL/4GL/PHP analysis workflow" as one workflow among many. `skills/`, `templates/source-code-analysis-schema.json`, and `.analysis-state/` are all hardcoded as if that single workflow *is* the application. The operator's actual need is broader: a local tool for running *any* long-lived, multi-stage LLM workflow — different prompts ("skills") per stage, potentially different local models per stage or per workflow, executed unattended against a large file set for hours or days — of which the legacy source/business-process analysis is simply the first concrete example. A native C# GUI — named **Analysis Pipeline Studio** — that owns orchestration directly (no PowerShell in the loop) should be built around that general model from the start, with the 9-stage legacy analysis shipping as the built-in default/sample workflow rather than the only thing the app can do.

## What Changes

- Reframe the product: the C# desktop app is a general local, multi-workflow LLM orchestration tool, not a legacy-code-analysis-only tool. A **workflow** = an ordered list of stages (each with its own prompt/role, target model/temperature/timeout, and parameters), a shared output schema, and one or more source roots to scan and queue files from. The legacy 9-stage source/business-process analysis ships as the built-in default workflow (`legacy-source-analysis`), not a hardcoded assumption baked into the app.
- New on-disk layout: `workflows/<workflow-id>/` holds one workflow's definition — `workflow.json` (id, display name, description, source root(s), optional workflow-level model/temperature defaults), `manifest.json` (ordered stage list, same shape as previously planned for `skills/pipeline-manifest.json` but scoped per workflow), `skills/<stage-id>/SKILL.md` (prompt/role content per stage), and `schema.json` (the workflow's output schema). `.analysis-state/` becomes per-workflow — `.analysis-state/<workflow-id>/{queue,states,checkpoints,locks,outputs}` — while `.analysis-state/app-config.json` stays one app-wide file for the shared LLM connection and worker defaults.
- **BREAKING**: Migrate the repository's actual, already-in-use `skills/`, `templates/source-code-analysis-schema.json`, and `.analysis-state/` content (queue, states, dozens of existing checkpoints, and outputs already on disk from real runs) into `workflows/legacy-source-analysis/` and `.analysis-state/legacy-source-analysis/` respectively, without losing any recorded history.
- **BREAKING**: Reimplement the orchestration currently in `scripts/generate_analysis_queue.ps1`, `scripts/run_analysis_pipeline.ps1`, `scripts/run_analysis_pipeline_parallel.ps1`, `scripts/queue_eta.ps1`, `scripts/reset_analysis_state.ps1`, and `scripts/stop_analysis_pipeline.ps1` natively in the app, generalized to operate on any workflow's queue rather than one hardcoded pipeline. The `.ps1` scripts are superseded and become unsupported once the app covers their functionality.
- Add a new `workflow-management` capability: a workflow gallery/catalog listing every defined workflow (built-in and operator-created), create/clone/rename/delete a workflow, configure its source root(s), switch which workflow the dashboard/editor/output browser/chatbot are currently scoped to, and import/export a workflow definition as a portable file so workflows can be shared as "recipes."
- Generalize the dashboard, stage editor, and output browser to operate on "the currently selected workflow" instead of "the pipeline": live queue/state/checkpoint views, token usage/ETA, and run controls (start/pause/resume/stop/reset) per workflow; a stage/schema editor scoped to the selected workflow's `manifest.json`/`SKILL.md`/`schema.json`; an output browser scoped to the selected workflow's `.analysis-state/<workflow-id>/outputs/`.
- Support multiple workflows running concurrently, each with its own worker pool and (optionally) its own LLM endpoint/model assignment, so different workflows can use different local LLM "skills" and keep running unattended for long stretches without contending for the same resources unless the operator wants them to.
- Make the app guided by a local LLM from the start: on first launch, before any other feature is usable, the operator must configure a local LLM connection (endpoint + model). That same connection powers an in-app chatbot with full control over workflow configuration and run state (creating/editing/deleting workflows, stage order, stage prompts, schema, settings, start/pause/resume/stop/reset) — it acts directly on low-risk changes and asks the operator for confirmation only when an action is high-risk (irreversible, destructive, or affecting already-completed work). The chatbot can now draft an entirely new workflow end-to-end from a natural-language description of the task, not just edit the one bundled pipeline.
- The chatbot can also draft small PowerShell scripts to carry out parts of the operator's workflow (bulk file/state operations, ad hoc queries or cleanup, scoped by default to the currently selected workflow's managed directories) and execute them when asked, under the same risk-gated model. This is workflow automation the operator requests on demand, not a new pipeline execution path — every workflow's stages are still run exclusively by the native C# engine.
- Add a run-configuration surface: Ollama endpoint/model, worker count, GPU (`CUDA_VISIBLE_DEVICES`) assignment, timeouts, and stall thresholds — as app-wide defaults, overridable per workflow — as editable, persisted settings.
- Decompose a stage into steps: a stage can now contain multiple ordered steps (each its own prompt/role, model/temperature/timeout override, and output), executed sequentially. Steps are the new atomic prompt-editing unit; a stage is a named grouping of steps. (Branching/parallel steps are an explicitly deferred future extension, not built now.)
- Add a `workflow-canvas` capability: a visual, node-based drawing pane showing a workflow's stages and their steps as connected nodes, used to add/remove/reorder stages and steps and to open a selected node's detail editor. Node layout (position) is stored separately from execution-relevant data so rearranging the canvas doesn't produce a meaningful diff to the run-affecting files.
- Add explicit save/load for the workflow currently being edited: canvas and editor changes are held as an in-memory draft with an unsaved-changes indicator; the operator explicitly saves (persisting to the workflow's `manifest.json`/step files) or discards, and reopening a workflow loads its last-saved definition.
- Add an `output-schema-editor` capability: the workflow's output schema is edited as a structured tree of nodes rather than raw JSON text, each node can be mapped to the stage/step that produces it, an unmapped node can be used to scaffold a new step directly, and the editor warns (without blocking) about nodes with no mapped producer. The pipeline engine merges each file's per-step outputs into one structured JSON result per the schema's node-to-step mapping and validates the merged result against the schema, same as today's single-stage validation.
- Add a `workflow-scheduling` capability: schedule a workflow run's start date/time (one-time or recurring), maximum run time, and retry count/interval by registering a native Windows Scheduled Task — Windows owns triggering, the execution time limit, and restart-on-failure behavior directly, rather than the app reimplementing a scheduler. The app supports a headless/unattended launch mode for scheduled triggers and hands off to an already-running instance instead of launching a duplicate.
- Explicitly out of scope: any workflow's configured source root(s) (e.g. `source code/` and `Processus affaires/` for the built-in `legacy-source-analysis` workflow) are analysis *inputs* only. The app reads file paths from them to build a workflow's queue but does not provide browsing/editing UI for their contents, and they are not part of the app's own codebase.

## Capabilities

### New Capabilities
- `workflow-management`: Workflow gallery/catalog, create/clone/rename/delete a workflow, configure its source root(s), select the active workflow, import/export a workflow definition, and explicit save/load of an in-progress editing draft.
- `pipeline-engine`: Native, per-workflow queue discovery, one-file-at-a-time (and multi-worker) sequential step-within-stage execution against a local Ollama-compatible endpoint, per-step output merging and schema validation, checkpointing, resume, and stall detection/retry — functionally replacing the `.ps1` pipeline scripts, with isolation between workflows so more than one can run concurrently.
- `pipeline-dashboard`: Live monitoring and run control UI for the selected workflow — queue/state/checkpoint views, step-level progress, token usage and ETA, start/pause/resume/stop/reset actions, plus a workflow switcher.
- `stage-definition-editor`: UI for viewing and editing the selected workflow's stages and their steps, each step's prompt/role definition and model parameters.
- `workflow-canvas`: Visual, node-based drawing pane for a workflow's stages and steps — add/remove/reorder/select nodes, with layout stored separately from execution-relevant data.
- `output-schema-editor`: Structured tree editor for a workflow's output schema, mapping each node to its producing stage/step and letting the operator scaffold a new step from an unmapped node.
- `output-browser`: UI for locating and viewing generated per-file artifacts and reports for the selected workflow.
- `workflow-scheduling`: Schedule a workflow run (start date/time, recurrence, max run time, retry count/interval) via native Windows Scheduled Tasks; manage scheduled runs from within the app; headless/unattended launch mode with single-instance handoff.
- `workflow-assistant`: Mandatory first-run LLM configuration wizard, plus a persistent in-app chatbot (backed by that same local LLM) with full read/write control over workflow management, workflow configuration, and run control — it applies low-risk changes directly and asks for confirmation only before high-risk/irreversible actions (including deleting an entire workflow). It can draft brand-new workflows from a description, and can draft and, within a restricted default scope, execute PowerShell scripts for ad hoc workflow tasks under the same confirmation model.

## Impact

- New C# application project (solution/executable) added to the repository; exact project layout is decided in `design.md`.
- New top-level `workflows/` directory holds every workflow definition, including the migrated built-in `legacy-source-analysis` one; `skills/` and `templates/source-code-analysis-schema.json` at the repository root are retired in favor of their per-workflow locations under `workflows/legacy-source-analysis/`.
- `.analysis-state/` gains a per-workflow subdirectory structure (`.analysis-state/<workflow-id>/...`); the repository's existing `.analysis-state/` content (real checkpoints/states/outputs already on disk) is migrated into `.analysis-state/legacy-source-analysis/` with no data loss. `.analysis-state/app-config.json` remains a single app-wide file.
- `scripts/*.ps1` become superseded: no longer the supported way to run any workflow once the app ships, though the files can remain for reference until removed in a later change.
- Content that was `skills/*/SKILL.md` and `templates/source-code-analysis-schema.json` becomes data the app reads and writes (via its editor) per workflow, rather than fixed files a person edits directly at the repo root; content must stay structured enough for the app to parse and re-render.
- Requires a local Ollama (or OpenAI-compatible) endpoint to be reachable, same as today; the app now enforces this at first launch via a setup wizard rather than assuming it silently. Individual workflows may be configured to use different endpoints/models.
- No change to the contents of `source code/`, `Processus affaires/`, or any other workflow's source root(s).
- A workflow's `manifest.json` gains a nested `steps` list under each stage; the migration in `design.md` wraps each of the legacy workflow's existing 9 stages as a single-step stage, so its run behavior is unchanged.
- New per-workflow `layout.json` holds canvas node positions, kept separate from `manifest.json` so visual rearrangement doesn't alter execution-relevant files.
- Adds a dependency on the Windows Task Scheduler API (e.g. the `TaskScheduler` managed wrapper) and requires the app to support a headless/unattended launch mode and single-instance detection.
