## 1. Bit-flip candidate generation

- [x] 1.1 Add a helper that, given a character, returns its 16 single-bit-flip variants (one per bit of the UTF-16 code unit), ordered to try common JSON syntax characters (`"`, `,`, `:`, `{`, `}`, `[`, `]`, space) before control characters.
  - `Get-BitFlipCharacterVariants` in the new shared `scripts\manifest_repair.ps1`. Each variant is tagged priority 0 (a common JSON syntax character), 1 (other printable ASCII) or 2 (control/non-ASCII) and the list is sorted by priority then bit index, so the sequence is fully deterministic; variants landing on a lone UTF-16 surrogate are dropped. Checked under both PowerShell 7.6.6 and Windows PowerShell 5.1: 16 variants, identical priorities (e.g. `"` 0x22 -> space 0x20 at bit 1; `2` 0x32 -> `"` 0x22 at bit 4; `?` 0x1020 -> space 0x20 at bit 12).

## 3. Bounded search and repair

- [x] 3.1 Define the search window size and total attempt budget — validate against this session's five real incident backups (`.analysis-state/queue/manifest.json.pre-repair-backup-*`) to pick values that reliably find the real fix for all five without excessive reparse count. Record the chosen values and why.
  - Chosen: **window 64 characters each side of the reported offset, 200 attempts, 5000 ms elapsed cap** (`Repair-SingleBitFlipCharacter` defaults, documented with the same evidence in `manifest_repair.ps1`).
  - Evidence: all three surviving backups are single-bit flips exactly **10 characters before** the offset the failing parse reports (0x1020 -> 0x0020 bit 12; 0x0032 -> 0x0022 bit 4 twice), so 64 is ~6x margin on the only distance ever observed. The real fixes are found at **attempts 14-15**, and a full-window search that finds nothing costs **1475 ms** on the live 7.0 MB manifest (200 attempts; the same input with 5 attempts takes 114 ms).
  - Caveat: only **3** backups exist on disk, not 5 -- the earlier incidents' backups are gone, and two of the three are the same incident (identical size and corruption). So this is empirical validation against 2 distinct corrupted snapshots covering both known classes, plus the 5 recorded incidents' documented shapes.
  - The elapsed cap exists because the per-candidate validator differs by engine: `System.Text.Json.JsonDocument` over a mutable char buffer costs 8-14 ms per full-document reparse on a 7.3 MB manifest, while Windows PowerShell 5.1's only alternative, `ConvertFrom-Json`, costs ~500 ms.
- [x] 3.2 Implement the bounded search: for each candidate position in the window (nearest the reported location first), for each of its bit-flip candidates (priority order per 1.1), substitute and attempt a full parse; return the first success within the attempt budget, or `$null` if exhausted.
  - Order is per *candidate tier* (all priority-0 candidates nearest-first, then tier 1, then tier 2) rather than strictly position-major: on the same fixtures the real fix lands at **rank 14-16** this way versus **rank 309-317** if every variant of one position is exhausted before moving on. Recorded in `design.md`.
  - Success returns the repaired text plus forensics (offset, both characters and code points, bit index, distance from the reported location, attempts used, elapsed) -- the callers log all of it.
  - Guard: text that already parses is never searched, because a bit flip *inside* a string value leaves the document valid and would otherwise be accepted as a "repair" of healthy data. Verified: 201/201 healthy snapshots returned `$null`.
- [x] 3.3 Wire this in as a second repair tier in `Read-Manifest` (`run_analysis_pipeline.ps1`), `queue_eta.ps1`, and `backfill_new_stage.ps1` — attempted after the existing non-ASCII repair when that doesn't apply or doesn't succeed, before falling through to existing retry/throw.
  - All three now dot-source `manifest_repair.ps1`; tier 1 was deduplicated into it (backfill's third, subtly different inline copy is gone) and `-join $chars` became `[string]::new($chars)` (2.3 s -> 6 ms on the 7.3 MB manifest).
  - The two readers with retry loops limit it to **one search per call** (a torn read is transient, and tier 1 still runs on every attempt), so the worst case is one bounded search plus the existing retries instead of one search per retry.
  - No other manifest reader needs it: `run_analysis_pipeline_parallel.ps1` leaves manifest parsing to the workers' `Read-Manifest`, `generate_analysis_queue.ps1` only writes the manifest, and `build_dependency_graph.ps1` reads per-file stage outputs, not the manifest.
  - Exercised end to end, not just helper-by-helper: `queue_eta.ps1` pointed at a temp copy of a real corrupted backup (it writes nothing) logs `Auto-repaired a single-bit-flip substitution in manifest.json at offset 4915911 ('2' 0x0032 -> '"' 0x0022, bit 4, 10 chars from the reported location, after 14 candidate reparses)` and then prints its normal queue report, exit 0 -- now check 4 of `verify_manifest_repair.ps1`.

  - `scripts\verify_manifest_repair.ps1` (new, read-only, re-runnable) replays every fixture that still exists: tier 1 recovers the non-ASCII one, tier 2 recovers that same one plus both `0x0032 -> 0x0022` ones, each in **14-15 of 200 attempts**, 236-559 ms of searching and 1.4-2.1 s end to end with tier 1 tried first. Every recovered document parses under `ConvertFrom-Json`, still carries its 1578 file entries, and the change is always exactly one bit.
- [x] 4.2 Time the worst-case repair path (window fully searched, no match found, falls through) against the current live manifest size, to confirm the bound actually holds in practice, not just in the attempt-count math.
  - Three characters damaged with two bits each in the live 7.0 MB manifest: returns `$null` and falls through in **1475 ms** end to end, well inside the 5 s elapsed cap -- and 5 attempts took 114 ms against the same input, confirming the attempt cap (not the clock) is what bounds the fast path.
- [x] 4.3 Confirm no false positives: run against a large sample of genuinely-healthy manifest snapshots (e.g. the backup copies that are NOT corrupted) and confirm the new tier is never invoked (since those parse successfully on the first attempt, before this tier is ever reached).
  - All three backups are corrupted and no other healthy manifest snapshot exists on disk, so the sample is the live manifest plus 200 `*.state.json` documents: all **201 parse on the first attempt**, so the catch path (and with it this tier) is never reached for them. Called *directly* on each with a parse-error message whose reported location is valid inside that document, the tier returned `$null` for all 201 (the "already parses" guard is what stops it), and tier 1 flagged nothing in any of them.

## Known limitation found while verifying

- A corruption that is **not** a single-bit flip can still be accepted if some single-bit-flip neighbour of some nearby character happens to parse. Reproduced deterministically: damaging one quote with two bits, the search "repaired" it by restoring a quote one character to the left (which parses, but renames that JSON key). This is the best-effort trade-off `design.md` already accepts -- the guarantee is "never accept a guess that doesn't parse", not "always find the true character" -- and the callers log exactly what changed and where, but it does mean a two-bit-flip incident can be papered over instead of stopping the run. Follow-ups if that matters: require the fix to be within a much smaller radius, or check the repaired document's shape against the JSON path the failing parse reported.
